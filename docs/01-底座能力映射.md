# 01 · 底座能力映射（中间件 → capabilities 模块）

> 核心思路：能力由仓库内的模块提供，不依赖独立服务。
> 所有原中间件退化为 `capabilities/` 下的一个模块，仅依赖本地文件、子进程和进程内调用；
> 不监听端口，不启动独立进程，不引入数据库、消息队列或反向代理。
> 每个能力模块采用适配器模式：接口约定不变、实现可以替换。

## 一、映射总表

| 原中间件/服务 | 第一阶段实现（本仓库内） | 接口契约 | 服务化回归路径（第二阶段起） |
|---|---|---|---|
| LiteLLM 网关 | `capabilities/llm/llm.py`（urllib 直连方舟 OpenAI-compatible API） | 契约 1 | 部署 LiteLLM 后，llm.py 仅换路由基址与鉴权头 |
| Mem0 | `capabilities/memory/memory.py`（jsonl 分片 + 朴素检索） | 契约 2 | 部署 Mem0 后换 REST 适配器，tag/user_id 语义对齐 |
| OpenViking | `capabilities/assets/assets.py`（manifest + 版本快照 + L0/L1/full） | 契约 3 | 部署 OpenViking 后换 viking:// REST 适配器（AGPLv3 红线不变：仅 API 调用，禁止源码合并） |
| MCP Gateway | `capabilities/tools/tools.py`（registry + policy 过滤 + 子进程直调） | 契约 4 | 插件如需保留 MCP 对外兼容，走 manifest `compat.mcp` 声明 |
| WeKnora（流程/知识承载） | `orchestration/`（flows + mailbox + gate） | 契约 5 | 面向业务人员的 Web 问答门户为第二阶段项（届时评估 WeKnora 重启或静态页面） |
| Prefect（曾被评估） | `orchestration/runner.py`（单宿主进程调度） | 契约 5 | 任务量超单机承载力时再评估，见 archive 评估报告 |
| Langfuse | `capabilities/trace/trace.py`（run 轨迹 jsonl） | — | 需要可视化轨迹时启用 WeKnora 内置 langfuse profile（错峰纪律保留） |
| Playwright MCP | `capabilities/scrape/scrape.py`（urllib 起步） | — | 动态页/需登录页再挂 playwright（MCP 或 Python SDK） |
| StarRocks | `db/*.db`（SQLite 文件库） | — | 数据量/并发超 SQLite 承载力时切 StarRocks（data/ 目录已留痕迹） |

## 二、零依赖裁决

1. **Python 3.15.2 系统自带**，零 pip 安装；标准库覆盖 sqlite3 / urllib / json / hashlib / tarfile / subprocess。
2. **PyYAML 缺失** → 自研 `capabilities/_yamlmini.py` 极简 YAML 子集解析器（注释/两级嵌套/标量/列表），
   配置文件写法限制见 02-目录规范.md §YAML 限制。这不是第三方组件，属本仓库自研代码。
3. **docker CLI 为可选依赖**：仅开发中心打包插件（`runtime: docker`）时子进程调用本机 OrbStack docker；
   新工程自身运行零容器、零端口、零 compose。第三方 docker 运行服务（联邦三件套等）全部脱离。
