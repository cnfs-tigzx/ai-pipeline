# MCP 工具控制规则（04-mcp-control-rule）

> 拆分自原 `.clinerules`「核心原则」与旧版规则「基础行为约束」，并按主题补充 stdio 模式与错误排查规范。
> 与 00-base-general.md 的确认策略（1.1）、日志规范（1.4）配合使用。

### 4.0 工具优先级（总原则）

- 所有任务必须优先调用 MCP 工具，工具优先级：filesystem（读写文件）> Terminal（shell/git）> playwright（网页抓取）
- 禁止编造内容、猜测文件、网页输出；不确定能力是否存在时，先列出可用工具清单再调用
- 禁止直接输出超 50 行的代码/json/文档，必须 write_file 写入磁盘（同 00-base-general.md §1.4）
- MCP 大响应直接落盘或同步工作台处理，禁止在对话中回显大段原始结果

### 4.1 服务调用纪律

- 调用前确认连接：MCP 服务未连接/未授权时先发起连接流程，禁止对未就绪服务直接调用
- 参数必须严格符合工具 schema：字段名、类型、必填项逐一核对，禁止凭记忆猜参数
- 一次调用只做一件事；无依赖的调用可并行，有依赖的调用必须等待上一步结果
- 敏感操作（写文件、执行命令、覆盖资源、破坏性命令）沿用 00-base-general.md §1.1 确认策略分级
- 失败重试最多一次；连续两次失败转入 4.3 排查流程，不盲目重试

### 4.2 stdio 模式约束

- stdio 型 MCP 服务以本地子进程方式启动（command + args + env + cwd），生命周期由客户端（Cline）管理
- 启动工作目录必须位于流水线工作根目录 `/Users/tigzx/workspace/ai-pipeline` 内，禁止指向系统目录
- 环境变量（API Key、token 等）仅注入服务配置，禁止写入仓库文件、日志或对话输出
- 服务 stdout 仅承载协议消息；调试输出走 stderr，避免污染 JSON-RPC 通道
- 长时间无响应按超时处理：先查子进程存活（ps），再查配置，禁止无限等待

### 4.3 错误排查（固定顺序）

1. **连接状态**：确认 MCP 服务是否已连接、授权是否有效
2. **服务进程**：stdio 型检查子进程是否存活（`ps` / 端口探测）；SSE/HTTP 型探测端点可达性
3. **配置核对**：command / args / env / cwd 是否正确，从 stderr 日志定位启动失败原因
4. **最小复现**：用最小参数单次调用，区分参数问题与服务问题
5. **恢复手段**：重启 MCP 服务或客户端后重试一次；仍失败则降级到等效工具（如 playwright 不可用 → fetch_web_content）
- 排查结论按 01-mem0-archive-rule.md §1.3 判断是否归档（仅任务闭环时写入）
